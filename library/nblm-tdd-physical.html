AI TRiSM Architectural Realization, Enforcement Mechanisms, and Evidence Inventory

1. Control Realization and Enforcement Points

1.1 Inline Proxies & API Gateways (Runtime Zone)

The Runtime Gateway functions as an AI Firewall operating at the boundary of the Runtime Zone. It establishes a synchronous control-plane intercept in front of all model endpoints, serving as a choke point for user prompts, agent-generated queries, draft completions, and context payloads retrieved from vector stores.

The architectural mechanics and control points enforced within this inline proxy infrastructure comprise:

  • Synchronous Prompt Inspection & Threat Mitigation (CP3): The gateway intercepts incoming prompts in real time to evaluate threat vectors defined in the OWASP Top 10 for LLM Applications (2025). It inspects token streams to block direct Prompt Injection (LLM01) and prevent System Prompt Leakage (LLM07). To mitigate Unbounded Consumption (LLM10), the gateway enforces strict request quotas, token bucket rate limits, and maximum context window allocations, truncating excess payloads before model invocation to limit compute usage and reduce agent blast radius.
  • Retrieval Access & Untrusted Content Verification (CP4): When integrating Retrieval-Augmented Generation (RAG) pipelines, data returned from vector databases and external retrieval sources is classified as untrusted content (CP4). The gateway inspects retrieved embeddings and payload text prior to context assembly to defend against indirect prompt injection, vector store manipulation, and Vector/Embedding Weaknesses (LLM08).
  • Synchronous Output Inspection & Data Leakage Prevention (CP6): The gateway evaluates model outputs before releasing responses to downstream consumers. Processing is configured based on output delivery mode:
    • Token-by-Token Streaming Inspection: Evaluates output buffers against regular expressions, entropy analyzers, and classification heads with minimal added latency.
    • Full-Frame Batch Evaluation: Holds the completed frame for deep semantic analysis prior to release. This inspection point explicitly blocks Sensitive Information Disclosure (LLM02) by redacting system instructions, proprietary code, trade secrets, and personally identifiable information (PII).
  • Policy Decision Engine & Deterministic Interception Logic: The gateway issues real-time synchronous check requests (allow, deny, or escalate) to an out-of-band Policy Engine. Interception behavior relies on application risk classification:
    • Fail-Closed Mode: Mandated for high-risk, healthcare, or financial workloads; any evaluation latency timeout or policy service disconnect results in an immediate HTTP 403 / System Blocked response.
    • Fail-Open Mode: Designated strictly for low-risk, public-facing informational use cases where availability takes precedence over speculative policy checks.
  • Telemetry Generation (CP7): Every transaction emits structured runtime telemetry pushed asynchronously to the Observability Zone and Interaction Log Store, ensuring inline policy enforcement does not bottleneck model serving.

1.2 Agents & Sidecars (Identity & Access Control)

Autonomous AI agents executing multi-step tool calls, data queries, and API actions are governed via an Agent Identity and Access Broker coupled with policy-as-code sidecar proxies deployed within the Runtime Zone.

The control architecture enforces identity boundaries and tool access rules:

  • SPIFFE/SPIRE Workload Identity Attestation: Shared service accounts are prohibited. Every autonomous AI agent receives a cryptographically verifiable workload identity using SPIFFE/SPIRE standards. The identity broker attests the agent's build environment, binary hash, and execution scope before issuing short-lived, cryptographically bound tokens.
  • OAuth 2.0 / OIDC Scoped Credentials & Least Privilege: Agents authenticate to external APIs, databases, and microservices through short-lived OAuth 2.0 / OIDC tokens issued JIT (Just-In-Time). Tokens are restricted to explicit read/write scopes required for the active sub-task.
  • Policy-as-Code Proxy Sidecars (CP5): Tool calls issued by an agent are routed through an egress sidecar proxy. The sidecar evaluates tool parameters against policy-as-code rules (e.g., Open Policy Agent/Rego) to enforce scoped tool execution (CP5). This prevents Excessive Agency (LLM06) by stripping unauthorized command parameters, enforcing read-only database connections, and preventing non-deterministic model loops from executing administrative commands.
  • Human-in-the-Loop Approval Gates: High-risk actions (e.g., financial transactions exceeding pre-set thresholds, system configuration modifications, or sensitive data deletions) trigger an out-of-band human-in-the-loop approval gate. The sidecar pauses execution and holds the transaction state until an authenticated supervisor approves or rejects the action via an enterprise notification service.

1.3 Release Pipeline & Build Zone (CI/CD Gates)

Control enforcement within the Build Zone governs model versioning, dataset validation, and release approval before artifacts are deployed to production serving infrastructure.

The CI/CD build gates incorporate the following mechanisms:

  • Pre-Release Evaluation Harness (CP2): Automated evaluation harnesses execute batch test suites against candidate model versions, fine-tuned weights, and system prompt configurations. Test sets quantify accuracy, reliability, toxicity, hallucination rates, and algorithmic bias.
  • Adversarial Red-Teaming Test Suites: Pre-deployment pipelines subject models to automated adversarial attack sets. These suites simulate prompt injection payloads, system prompt extraction attempts, and data exfiltration vectors to measure defense robustness.
  • Automated Quality & Security Release Gating: Model artifacts are registered in the Model Registry with an explicit Draft status. Automated CI/CD gates evaluate test results against established governance baseline metrics. If a candidate model meets or exceeds required performance thresholds and passes safety evaluations, the release gate signs the model artifact and updates its registry state to Approved (CP2); otherwise, deployment pipelines abort automatically.

1.4 Governance Zone Infrastructure

The Governance Zone maintains enterprise-wide visibility, data classification, and lifecycle oversight across all deployed AI assets and storage repositories.

Governance infrastructure is realized through two core platform capabilities:

  • Data Map & Classifier (CP1): Scans enterprise databases, object storage, and vector indices to build a continuous data map. It identifies, categorizes, and applies sensitivity labels (e.g., Confidential, PII, Restricted) to datasets (CP1). These labels dictate whether data can be used for training, fine-tuning, or retrieval context within RAG applications.
  • AI Asset Registry: Maintains a central inventory of every AI model version, application endpoint, data pipeline, fine-tuning dataset, and autonomous agent deployed across the enterprise. The registry maps asset ownership, risk classification tiers, upstream model lineage, and associated policy profiles, establishing a systemic audit foundation for enterprise risk governance.

4. Deployment Realities in Regulated and Government Environments

4.1 EU AI Act Provisions (Regulation (EU) 2024/1689)

Legal obligations and explicit exclusions governing AI system deployment within the European Union are defined in Regulation (EU) 2024/1689 (Article 2):

  • Scope of Applicability (Article 2(1)): Applies to providers placing on the market or putting into service AI systems, or placing on the market general-purpose AI (GPAI) models in the EU, irrespective of whether providers are established within the Union or in a third country; deployers of AI systems located within the EU; and providers/deployers located in a third country where output produced by the AI system is used within the EU.
  • Military, Defence, and National Security Exclusion (Article 2(3)): The Regulation explicitly does not apply to AI systems where and in so far as they are placed on the market, put into service, or used—with or without modification—exclusively for military, defence, or national security purposes, regardless of the type of entity carrying out those activities.
  • Scientific Research & Development Exclusion (Article 2(6)): The Regulation does not apply to AI systems or AI models (including their outputs) specifically developed and put into service for the sole purpose of scientific research and development.
  • Pre-Market Research and Development Exclusion (Article 2(8)): The Regulation does not apply to any research, testing, or development activity regarding AI systems or models prior to being placed on the market or put into service. Testing in real-world conditions is explicitly not covered by this exclusion.
  • Personal Non-Professional Use Exclusion (Article 2(10)): The Regulation does not apply to obligations of deployers who are natural persons using AI systems in the course of a purely personal, non-professional activity.
  • Free and Open-Source License Exclusion (Article 2(12)): The Regulation does not apply to AI systems released under free and open-source licenses, unless they are placed on the market or put into service as high-risk AI systems or fall under Article 5 (prohibited AI practices) or Article 50 (transparency obligations).
