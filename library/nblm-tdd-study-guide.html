AI-TRISM and AI Risk Management Study Guide

This comprehensive study guide synthesizes key concepts, architectural frameworks, risk profiles, regulatory standards, and practice materials for AI Trust, Risk, and Security Management (AI-TRISM). The material is derived directly from technical architecture specifications, NIST standards (AI RMF 1.0 / NIST AI 100-1 and NIST AI 600-1), ISO/IEC 42001 crosswalks, the EU AI Act (Regulation (EU) 2024/1689), and the OWASP Top 10 for LLM Applications (2025).

1. Executive Overview & Key Architectural Concepts

1.1 Conceptual Architecture & Core Capabilities

AI-TRISM provides a unified control framework addressing the unique vulnerabilities of machine learning systems, such as non-deterministic behavior, data drift, natural-language attack surfaces, and inscrutable model states.

The conceptual architecture establishes eight fundamental capabilities (C1–C8) structured across governing pillars and layers:

Capability ID Capability Name Delivered Outcome Sourced Framework Origin
C1 AI Catalog Single centralized inventory of all AI models, applications, and agents (including shadow AI). Gartner guidance (via IBM)
C2 AI Data Mapping Visibility into data lineage: what data each AI asset reads, trains on, retrieves, and emits. Gartner guidance (via IBM)
C3 Continuous Assurance & Evaluation Scheduled and pre-release testing for accuracy, bias, robustness, and vulnerability. Gartner guidance (via IBM)
C4 Runtime Inspection & Enforcement Real-time policy application on incoming prompts, retrieved text, model outputs, and tool calls. Gartner guidance / Zscaler
C5 Explainability & Monitoring Operational capability to interpret decisions, trace feature outputs, and detect drift/anomalies. NIST AI RMF / Zscaler
C6 Model Lifecycle Governance (ModelOps) Controlled release gates, versioning, deployment, retraining, and safe decommissioning. Zscaler
C7 Information & Privacy Governance Data protection across training sets, prompt payloads, vector retrievals, and generated responses. Zscaler
C8 Compliance Mapping & Evidence Traceable mapping of controls to NIST AI RMF, ISO/IEC 42001, and legal regulations with tamper-evident records. NIST AI RMF / ISO Crosswalk

Key Conceptual Actors

  • AI Risk Owner: Sets enterprise risk tolerance and approves AI use cases.
  • Model Builder: ML engineers/data scientists who train, evaluate, and release models.
  • Application Owner: Teams integrating AI capability into customer/internal features.
  • Security Operations (SecOps): SOC personnel monitoring runtime alerts and AI-specific threats.
  • Privacy & Compliance Officer: Maps regulatory obligations to technical controls and evidence.
  • End User: Internal or external human actor submitting prompts (untrusted input source).
  • AI Agent: Autonomous software executing multi-step tools/actions (untrusted by default; least-privilege bound).
  • Third-Party Model/Tool Provider: External API or plugin provider introducing supply-chain risk.

Logical Components

  1. AI Asset Registry: Inventory store recording models, applications, agents, datasets, owners, and risk tiers.
  2. Data Map & Classifier: Assigns sensitivity labels and logs data lineage across training and retrieval stores.
  3. Policy Engine: Evaluates inputs against policies to return allow, deny, or escalate decisions.
  4. Evaluation & Red-Team Harness: Executes automated attack sets and quality benchmarks during CI/CD and on schedule.
  5. Runtime Gateway: Inline reverse proxy inspecting prompts, retrieved context, generated outputs, and tool calls.
  6. Agent Identity & Access Broker: Issues short-lived, least-privilege tokens for AI agents invoking enterprise tools.
  7. Monitoring & Behavior Analytics: Analyzes production telemetry for drift, latency anomalies, and policy violations.
  8. Explainability Service: Generates global and local feature-attribution explanations for model outputs.
  9. Model Registry & Release Pipeline: Manages model versions, evaluation gating, and retirement triggers.
  10. Evidence & Audit Store: Immutable, append-only repository storing control execution logs and test results.
  11. Incident Handler: Interfaces with SOC tooling to manage containment actions upon policy breach or anomaly detection.

Primary Logical Data Flows (F1–F9)

  • F1 (Request Check): User/Agent $\rightarrow$ Runtime Gateway (Sync: Prompt payload, identity context).
  • F2 (Policy Decision): Runtime Gateway $\rightarrow$ Policy Engine (Sync: Request metadata, evaluated rules).
  • F3 (Retrieval): AI Application $\rightarrow$ Vector Store / RAG Source (Sync: Untrusted retrieved content).
  • F4 (Tool Call): AI Application $\rightarrow$ Access Broker / External Tools (Sync: Scoped credential request & action).

1.5 Threat Mapping: OWASP Top 10 for LLM Applications (2025)

Risk ID & Title Vulnerability Point Sourced Mitigation Controls
LLM01: Prompt Injection CP3 (Gateway Input), CP4 (RAG Retrieval) Segregate external content; validate output structure; enforce least privilege; require human approval for high-risk actions.
LLM02: Sensitive Information Disclosure CP6 (Gateway Output), System Prompt Pre-training data sanitization; strict output inspection filters (note: system prompt rules alone can be bypassed).

LLM05: Improper Output Handling Downstream Application Consumers Treat all LLM outputs as untrusted input; encode output prior to passing to web browsers, shells, or SQL engines.
LLM06: Excessive Agency CP5 (Tool Invocation) Grant minimum viable permissions to agents; enforce human-in-the-loop (HITL) authorization for critical functions.
LLM07: System Prompt Leakage CP6 (Model Completions) Sanitize prompts prior to deployment; screen completions for matches against system prompt strings.
LLM08: Vector and Embedding Weaknesses CP4 (RAG Vector Store) Encrypt embeddings in transit/rest; enforce strict access control lists (ACLs) on vector query endpoints.
LLM09: Misinformation CP6 (Output Completions) Ground outputs via retrieval verification; display confidence scores; cross-check facts against structured stores.
LLM10: Unbounded Consumption CP3 (Gateway Endpoint) Set rate limits, token quotas, max context-window boundaries, and hard financial budgets per execution.

1.6 Standards Profile & NIST AI RMF Core Architecture

NIST AI RMF 1.0 (NIST AI 100-1) Structure

NIST AI RMF divides risk management into four Core Functions executed iteratively:

  1. GOVERN: Cross-cutting function establishing organizational risk culture, legal context, risk tolerance, workforce diversity, accountability structures, third-party oversight, and decommissioning procedures.
  2. MAP: Establishes context, categorizes the AI system, identifies targeted benefits/costs, maps legal/component risks, and characterizes impacts to individuals, groups, and society.
  3. MEASURE: Applies quantitative and qualitative tools to test, evaluate, verify, and validate (TEVV) trustworthy characteristics, track emergent risks, and assess control effectiveness.
  4. MANAGE: Allocates risk management resources, prioritizes risk treatments (mitigate, transfer, avoid, accept), documents residual risk, and executes incident response and recovery plans.

NIST 7 Trustworthiness Characteristics

  1. Valid and Reliable: Requires accurate operation under expected conditions over time; generalizability to non-training settings.
  2. Safe: Systems must not cause harm to human life, health, property, or the environment under defined operational conditions.
  3. Secure and Resilient: Ability to withstand adverse events or adversarial attacks (evasion, extraction, poisoning) and degrade gracefully.
  4. Accountable and Transparent: Provides context-appropriate access to system design, data provenance, and decision rationale to enable auditability.
  5. Explainable and Interpretable: Describes underlying operational mechanisms (explainable) and the functional contextual meaning of outputs (interpretable).
  6. Privacy-Enhanced: Safeguards individual autonomy and identity using data minimization, anonymization, and privacy-enhancing technologies (PETs).
  7. Fair – with Harmful Bias Managed: Addresses equality and equity by analyzing systemic, computational/statistical, and human-cognitive biases.

1.8 Regulation (EU) 2024/1689 (EU AI Act) Core Definitions & Scope

  • AI System Definition (Article 3(1)): A machine-based system designed to operate with varying levels of autonomy that may exhibit adaptiveness after deployment, and that, for explicit or implicit objectives, infers from the input it receives how to generate outputs such as predictions, content, recommendations, or decisions that can influence physical or virtual environments.
  • Provider (Article 3(3)): Natural or legal person, public authority, agency, or body that develops an AI system or general-purpose AI model (or has one developed) and places it on the market or puts it into service under its own name/trademark.
  • Deployer (Article 3(4)): Natural or legal person, public authority, agency, or body using an AI system under its authority, except for personal non-professional activity.
  • Out-of-Scope Activities (Article 2): Systems used exclusively for military, defense, or national security purposes; scientific research and development; pre-market research/testing prior to real-world operational deployment; purely personal non-professional deployer activities.

3. Answer Key for Short-Answer Questions

1. Definition of AI System and Unique AI Risks:

Answer: NIST AI RMF 1.0 defines an AI system as an engineered or machine-based system that can, for a given set of objectives, generate outputs such as predictions, recommendations, or decisions influencing real or virtual environments. Unlike traditional software, AI system risks stem from data dependencies, dataset staleness/drift, opacity, inscrutable decision logic across billions of parameters, socio-technical context sensitivity, non-deterministic outputs, and novel attack surfaces such as prompt injection and model extraction.

2. NIST AI RMF Functions & Cross-Cutting Governance:

Answer: The four core functions are GOVERN, MAP, MEASURE, and MANAGE. GOVERN is designated as a cross-cutting function because organizational policies, accountability structures, risk tolerances, and governance culture must be continually infused into and direct the technical activities carried out across MAP, MEASURE, and MANAGE throughout the AI lifecycle.

3. Eight Core Capabilities (C1–C8):

Answer: The eight capabilities are: C1 AI catalog, C2 AI data mapping, C3 Continuous assurance and evaluation, C4 Runtime inspection and enforcement, C5 Explainability and monitoring, C6 Model lifecycle governance (ModelOps), C7 Information and privacy governance, and C8 Compliance mapping and evidence storage.

4. Policy Engine vs. Runtime Gateway vs. Model Endpoint:

Answer: The Runtime Gateway sits inline to intercept incoming user/agent prompts and outgoing model completions. Upon receiving a request, the Gateway queries the Policy Engine synchronously, passing metadata to evaluate policy rules. The Policy Engine returns an explicit allow, deny, or escalate decision; the model itself is never trusted to enforce organizational policy on its own inputs or outputs.

5. Seven NIST Trustworthiness Characteristics:

Answer: The seven characteristics are: 1) Valid and Reliable, 2) Safe, 3) Secure and Resilient, 4) Accountable and Transparent, 5) Explainable and Interpretable, 6) Privacy-Enhanced, and 7) Fair – with Harmful Bias Managed.

6. OWASP LLM01 Prompt Injection & Mitigations:

Answer: LLM01 Prompt Injection occurs when untrusted user inputs or retrieved third-party text manipulate an LLM's context window to alter its intended behavior or execute unauthorized commands. Sourced mitigations include segregating external untrusted content from system instructions, enforcing input/output format validations, restricting agent model privileges to minimum viable thresholds, and requiring human approval for sensitive actions.

7. Five Physical Deployment Zones:

Answer: The physical deployment zones are: 1) Build Zone (pipelines, evaluation harness), 2) Runtime Zone (gateways, model endpoints, access brokers), 3) Observability & Security Zone (monitoring, incident handling), 4) Governance Zone (asset registries, data classifiers, policy engines, evidence stores), and 5) External Zone (clients, third-party model APIs, data stores).

8. EU AI Act Key Definitions:

Answer: Under Article 3 of Regulation (EU) 2024/1689, an AI System is an autonomous machine-based system inferring how to generate outputs (content, predictions, decisions) influencing environments. A Provider is any entity that develops (or has developed) an AI system/model and places it on the market under its own name/trademark. A Deployer is any natural or legal person using an AI system under its authority, excluding personal non-professional use.

9. AI-TRISM Build Order Sequence & Step 1 Rationale:

Answer: The sequence is: 1) Evidence Store, 2) Asset Registry, 3) Data Map, 4) Policy Engine, 5) Agent Identity Broker, 6) Gateway (Monitor Mode), 7) Evaluation Harness, 8) Monitoring/Incidents, 9) Gateway (Enforce Mode), and 10) Compliance Mapping. The Evidence Store must be deployed first so that every subsequent asset registration, data classification scan, and policy decision immediately generates an immutable, traceable audit trail.

10. ISO/IEC 42001 Mapping for GOVERN 1.6:

Answer: NIST subcategory GOVERN 1.6 (establishing mechanisms to inventory AI systems) maps to ISO/IEC 42001 Annex B resource management controls: B.4.2 (Resource documentation), B.4.3 (Data resources), B.4.4 (Tooling resources), B.4.5 (System and computing resources), and B.4.6 (Human resources).

5. Comprehensive Glossary

  • AI Actor: Individuals or entities who play an active role in the AI system lifecycle, including designers, developers, deployers, evaluators, auditors, and operators (NIST AI 100-1 / OECD).
  • AI Asset: Any machine learning model, fine-tuned binary, wrapper application, autonomous agent, vector store, or training dataset under enterprise governance.
  • AI Catalog (Capability C1): A centralized enterprise registry documenting every deployed, operational, or experimental AI system, including asset ownership, lifecycle state, and risk classification.
  • AI Data Mapping (Capability C2): The process of tracking and documenting the flow, sensitivity labels, and retention parameters of data read, trained on, retrieved by, or emitted from AI assets.
  • AI Risk: The composite measure of the probability of an AI-related event occurring and the magnitude or severity of negative consequences experienced by individuals, organizations, society, or the environment (NIST AI 100-1 / EU AI Act).
  • AI System (EU AI Act Definition): A machine-based system designed to operate with varying levels of autonomy that may exhibit adaptiveness after deployment, and that infers from received inputs how to generate outputs influencing physical or virtual environments (Regulation (EU) 2024/1689).
  • AI System (NIST Definition): An engineered or machine-based system that can, for a given set of objectives, generate outputs such as predictions, recommendations, or decisions influencing real or virtual environments (NIST AI 100-1).
  • Agent Identity and Access Broker: A logical security component responsible for issuing unique workload identities, scoped short-lived credentials, and least-privilege tool access to autonomous AI agents.
  • Conformity Assessment: The process of demonstrating whether specified requirements relating to a high-risk AI system (under Chapter III, Section 2 of the EU AI Act) have been fulfilled.
  • Continuous Assurance & Evaluation (Capability C3): Scheduled, continuous automated testing executed across the AI lifecycle to verify model performance, robustness, safety, and bias boundaries against standardized benchmarks.
  • Deployer: Any natural or legal person, public authority, agency, or body using an AI system under its authority, except where used for purely personal non-professional activity (Regulation (EU) 2024/1689).
  • Evidence & Audit Store: An append-only, tamper-evident repository that logs all policy decisions, evaluation outcomes, approval records, and runtime telemetry for audit and compliance verification.
  • Explainability: Representation of the internal technical mechanisms underlying an AI system’s operations and decision processes (NIST AI 100-1).
  • Interpretability: The contextual meaning of an AI system’s output in terms of its designed functional purpose (NIST AI 100-1).
  • ModelOps (Capability C6): Model Lifecycle Governance encompassing operational version control, controlled release gating, CI/CD testing integration, production deployment, monitoring, retraining, and safe decommissioning.
  • Policy Engine: A centralized service that stores organizational risk rules as code and evaluates request context from runtime proxies to return execution verdicts (allow, deny, escalate).
  • Prompt Injection (OWASP LLM01): An attack technique where adversarial instructions embedded in user inputs or retrieved content manipulate an LLM's context window to override system constraints or execute unauthorized commands.
  • Provider: A natural or legal person or public authority that develops an AI system or general-purpose AI model (or has one developed) and places it on the market under its own name or trademark (Regulation (EU) 2024/1689).
  • Residual Risk: The remaining risk level after risk treatment controls have been implemented (ISO Guide 73 / NIST AI 100-1).
  • Runtime Gateway (Capability C4): An inline network proxy or API middleware that inspects prompts, context, completes text, and tool calls to enforce security and privacy policies in real time.
  • TEVV (Test, Evaluation, Verification, and Validation): A foundational set of continuous technical tasks performed throughout the AI lifecycle to ensure an AI system satisfies system specifications, legal constraints, and performance baselines.
  • Trustworthiness Characteristics: The seven key attributes defined by NIST AI 100-1 that define a trustworthy AI system (Valid & Reliable, Safe, Secure & Resilient, Accountable & Transparent, Explainable & Interpretable, Privacy-Enhanced, Fair with Harmful Bias Managed).
