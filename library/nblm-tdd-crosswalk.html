Enterprise Architecture Crosswalk: AI-TRISM Mappings to TOGAF ADM and DoDAF Viewpoints

1. Architectural Scope and Abstraction Methodology

To integrate Artificial Intelligence Trust, Risk, and Security Management (AI-TRISM) into standard enterprise architecture frameworks, architectural elements must be categorized across explicit abstraction levels. This crosswalk establishes a formal mapping between AI-TRISM operational capabilities, logical components, physical realization patterns, the Open Group Architecture Framework Architecture Development Method (TOGAF ADM), and the Department of Defense Architecture Framework (DoDAF) viewpoints.

Architectural Abstraction Altitudes

  • Conceptual Altitude ("What and Why"): Establishes high-level operational concepts, capabilities, actors, and fundamental domain concepts without referencing vendor products, license Stock Keeping Units (SKUs), service interfaces, or specific deployment regions.
  • Logical Altitude ("Which Parts and How They Talk"): Defines vendor-neutral logical components, system interfaces, logical data entities, attributes, entity-relationship structures, and interaction flows. It specifies component responsibilities, input/output structures, and synchronization behaviors independent of physical hosting or deployment topologies.
  • Physical Altitude ("What is Deployed and Where"): Specifies physical realization patterns, deployment topologies partitioned into designated Trust Boundaries (TB1–TB5), storage implementation mechanisms, standards profiles, and explicit build sequences.

Governance Rules for Source Silence and Unverified Attributes

To maintain rigorous enterprise architecture fidelity, the following strict grounding rule governs this crosswalk:

Source Silence Rule: If an element, mapping, interface, cloud deployment environment (e.g., Commercial, GCC, GCC High, DoD/Gov Secret), or physical SKU is not directly documented within the provided source context, it must be explicitly designated as UNSUPPORTED / SILENT or UNVERIFIED. Extrapolations, external assumptions, or ungrounded inferences are strictly prohibited.

Application Architecture Integration Patterns across AI Archetypes (TOGAF Phase C)

To ensure precise operational governance, Phase C Application Architecture must differentiate interface behaviors and enforcement controls across four primary AI integration archetypes:

  1. Classical Machine Learning Archetype:
    • Data Path & Interfaces: Tabular dataset ingestion $\rightarrow$ Feature Store batch/stream reads $\rightarrow$ Deterministic scoring endpoint.
    • Governance Behavior: Intercepted at pre-deployment release gates via CMP-04 (Evaluation Harness) to verify dataset provenance and baseline accuracy metrics. Runtime enforcement (CMP-05) monitors inference payload schemas and feature distribution drift asynchronously (F6, F9), triggering CMP-08 (Explainability Service) for local feature-attribution scoring upon output delivery.
  2. LLM Applications Archetype:
    • Data Path & Interfaces: User natural-language prompt $\rightarrow$ Runtime Gateway (CMP-05) $\rightarrow$ Model Endpoint $\rightarrow$ Runtime Gateway (CMP-05) $\rightarrow$ User Response.
    • Governance Behavior: Requires synchronous inline proxying. CMP-05 intercepts incoming prompts to evaluate formatting rules, detect direct prompt injection (LLM01), and verify user token scopes via CMP-03 (Policy Engine). Draft responses are synchronously held at F5 (Output Check) to execute real-time PII redacting, sanitization, and system prompt leakage checks (LLM02, LLM07) prior to client emission.
  3. Retrieval-Augmented Generation (RAG) Archetype:
    • Data Path & Interfaces: User prompt $\rightarrow$ Gateway inspection $\rightarrow$ Vector Store lookup (F3) $\rightarrow$ Context assembly $\rightarrow$ Model Endpoint $\rightarrow$ Output inspection (F5).
    • Governance Behavior: Extends LLM application patterns by classifying all retrieved vector store embeddings and text chunks as untrusted external content (F3). CMP-02 (Data Map and Classifier) enforces document sensitivity labels, ensuring the vector database query executes under the querying user's security clearance context to prevent data leakage (LLM02). Inline proxy CMP-05 inspects assembled context windows for indirect prompt injection vectors before forwarding payloads to the host LLM.
  4. Autonomous AI Agents Archetype:
    • Data Path & Interfaces: Operational Goal $\rightarrow$ Agent reasoning loop $\rightarrow$ Tool Call request (F4) $\rightarrow$ Identity Broker (CMP-06) validation $\rightarrow$ System API execution.
    • Governance Behavior: High-risk execution model governing variable autonomy (Agency concept CON-7). Agents are treated as untrusted runtime actors (ACT-7). Tool calls (F4) bypass direct model execution and are intercepted by CMP-06 (Agent Identity and Access Broker). CMP-06 issues short-lived, just-in-time (JIT) cryptographically bound access tokens granting least-privilege API scope. High-impact operational calls (e.g., database writes, financial transactions) force synchronous policy escalation to ACT-1 / ACT-3 for mandatory human-in-the-loop (HITL) approval prior to execution ([S7 / OWASP Top 10 LLM 2025]).

Architectural Dependency Justification: CMP-10 (Evidence Store) must be established at Step 1 to guarantee an immutable, unbroken telemetry baseline before any operational assets, policies, or gateways are introduced. Asset registration (CMP-01) and data classification (CMP-02) must precede policy engine activation (CMP-03), as rules cannot be evaluated against unknown assets or unclassified data paths. CMP-06 (Identity Broker) relies on policy rules established in CMP-03. The Runtime Gateway (CMP-05) is initially deployed in non-blocking monitor mode (Step 6) to gather baseline traffic metrics, feed security observability (CMP-07/CMP-11, Step 8), and allow release pipeline testing (CMP-04, Step 7) before active enforcement blocking is toggled (Step 9). Finally, regulatory packaging (Step 10) aggregates audit outputs across the mature pipeline.

The 10-step reference build sequence is executed as follows:

  1. Step 1: Evidence and Audit Store (CMP-10 / STR-2): Deploy append-only storage in Governance Zone (TB4) configured with customer-managed keys [S10 / AWS Builder AI TRiSM] to capture baseline telemetry prior to component activation.
  2. Step 2: AI Asset Registry (CMP-01 / STR-1): Instantiate asset catalog in Governance Zone (TB4) and initiate automated discovery scans to establish baseline inventory [S8 / IBM AI TRiSM].
  3. Step 3: Data Map and Classifier (CMP-02): Connect data classification engines to catalog assets and tag sensitive training/retrieval paths [S8 / IBM AI TRiSM].
  4. Step 4: Policy Engine (CMP-03 / STR-4): Deploy policy-as-code evaluation engine configured with initial NIST Govern rules [S2 / NIST AI 100-1].
  5. Step 5: Agent Identity and Access Broker (CMP-06): Configure workload identity provider in Runtime Zone (TB2) to issue scoped JIT tokens [S12 / CSA Keynote Darktrace].
  6. Step 6: Runtime Gateway in Monitor Mode (CMP-05): Deploy inline proxy in Runtime Zone (TB2) in non-blocking monitor mode to establish baseline traffic telemetry.
  7. Step 7: Evaluation and Red-Team Harness (CMP-04): Integrate automated security/accuracy evaluation harnesses into CI/CD release pipelines in Build Zone (TB1) [S11 / Bo Li UIUC Talk].
  8. Step 8: Monitoring, Analytics, and Incident Handling (CMP-07 / CMP-11): Stand up observability pipelines in Zone TB3 and link alert outputs to existing SOC tooling [S9 / Zscaler AI TRiSM].
  9. Step 9: Gateway Mode Transition to Enforce: Switch Runtime Gateway to active blocking mode on a per-use-case basis (evaluating fail-closed vs. fail-open parameters).
  10. Step 10: Compliance Mapping and Evidence Packaging (C8): Execute automated NIST AI RMF to ISO/IEC 42001 control mappings to produce initial regulatory audit packs [S4 / NIST-to-ISO Crosswalk].
