Business Explanation

Business Explanation

AI TRiSM is the name used for the controls around AI systems. This map shows what the study day covers: who is accountable, which capabilities the architecture must provide, how those capabilities become components and zones, which outside systems are in play, and where attacks land. It is a study map, not a product design, and several vendor and government-cloud cells stay unverified on purpose.

AI-TRISM

  • Context and boundary
  • Scope: Gartner AI TRiSM (AI Trust, Risk and Security Management) as an architecture. In scope, all four layers: explainability and model monitoring; ModelOps and lifecycle governance; AI application security (prompt injection, data leakage, adversarial attacks, guardian agents); privacy and compliance. Out of scope: (assumed) building or training models, and deep product tutorials for any single vendor.
  • Naming caution: that intake list matches the pillar crosswalk in secondary sources [S9] [S10], not layer names printed on a Gartner-owned page. [S1] says "four layers" and does not name them. Secondary sources name the layers as AI governance, AI runtime inspection and enforcement, information governance, and infrastructure and stack [S9]. See Debate 1.
  • Cloud / tenant: Vendor-neutral reference architecture. No single cloud. Vendors appear in the third-party inventory only, with gov-cloud support marked per row.
  • Anchor rule: design review anchors to ISO/IEC 42001 (certifiable via independent bodies) [S14] [S15] and NIST AI RMF plus the GenAI profile (voluntary) [S2] [S3]. TRiSM is the capability and tool map, not a conformance scheme. See Debate 2.
  • Still cannot claim: primary Gartner layer or pillar names from a Gartner-owned page; Ray 2026 full text [S13]; a finished NIST AI 600-1 risk-to-pillar map; measured guardrail detection rates.
  • Conceptual: capabilities, actors
  • Problem: conventional controls do not cover non-deterministic behavior, data drift, or natural-language attacks [S7] [S8] [S9].
  • Actors, trusted but constrained: AI risk owner, model builder, application owner, security operations, privacy and compliance officer.
  • Actors, untrusted or external: end user (untrusted input), AI agent (untrusted by default, least privilege), third-party model or tool provider [S7], auditor or regulator (demands evidence).
  • C1 AI catalog: one inventory, including shadow AI [S8].
  • C2 AI data mapping: which data each system reads, trains on, and emits [S8].
  • C3 Continuous assurance and evaluation [S8].
  • C4 Runtime inspection and enforcement [S8] [S9].
  • C5 Explainability and monitoring, from pillars plus NIST [S9] [S2].
  • C6 Model lifecycle governance (ModelOps) [S9].
  • C7 Information and privacy governance [S9].
  • C8 Compliance mapping and evidence to NIST AI RMF, ISO/IEC 42001, and applicable law [S2] [S4].
  • Concepts: AI asset, risk, seven NIST trustworthiness characteristics, policy, control, evidence, agency [S2] [S7].
  • Open: fairness and safety have no clearly named pillar (Debate 4). Whether C2 stands apart from C7 depends on unread primary layer definitions.
  • Altitude: no product names. Full note: 01 - Conceptual View.
  • Logical: components, data entities, flows
  • Proposed decomposition (no ledger source prescribes these boundaries). Each capability has at least one component.
  • Components: AI asset registry (C1); data map and classifier (C2, C7); policy engine (C4, C6, C8); evaluation and red-team harness (C3); runtime gateway (C4); agent identity and access broker (C4); monitoring and behavior analytics (C5); explainability service (C5); model registry and release pipeline (C6); evidence and audit store (C8); incident handler (C3, C4, C5).
  • Entities: AI asset, model version, dataset, policy, control, requirement, evaluation result, interaction record, incident, evidence item.
  • Runtime path F1 to F6: request check, policy decision, retrieval, tool call, output check, interaction logging. Release gate F7, evidence capture F8, drift alert F9.
  • Red (untrusted content): user or agent prompt into the gateway; retrieved text back into the application [S7].
  • Decisions: gateway is the choke point but the access broker does not depend on it (Debate 3); policy sits outside the model [S7]; evidence is a by-product (F8); retrieval data is untrusted [S7].
  • Full note: 02 - Logical View.
  • Physical: services, clouds, SKUs, agents
  • Vendor-neutral: no single cloud. Physical view shows generic deployment zones; gov-cloud support is marked per vendor row in the inventory.
  • Zones and trust boundaries: TB1 build (registry, release pipeline, evaluation harness); TB2 runtime (gateway, model serving, agent identity broker, explainability); TB3 observability and security (monitoring, incident handler); TB4 governance (asset registry, data map, policy engine, evidence store); TB5 external (users and client agents, third-party model providers, enterprise data and retrieval stores).
  • Red links: prompts from clients into the gateway; retrieval from enterprise data into serving [S7].
  • License, SKU, region, and commercial / GCC / GCC High / DoD rows are UNVERIFIED. No vendor product page was read for those cells.
  • Stores: registry, evidence (append-only; customer-managed keys recommended, one cloud example only [S10]), interaction log, policy store. Retention mostly UNVERIFIED.
  • Standards (StdV-1): NIST AI RMF 1.0 voluntary [S2]; NIST AI 600-1 voluntary [S3]; ISO/IEC 42001:2023 certification route via independent bodies [S5] [S14] [S15]; EU AI Act binding where it applies [S6]; OWASP Top 10 for LLM Applications 2025 optional [S7]; NIST to ISO 42001 crosswalk optional [S4].
  • Full note: 03 - Physical View.
  • Integration: third-party and external systems, APIs, identity
  • Inventory themes, not a buy list. A named vendor is not a recommendation. Gov-cloud is UNVERIFIED on every row.
  • Themes: third-party model providers; model registry and MLOps; AI guardrail or AI firewall; secure access / SSE (Zscaler named only as a vendor explainer [S9]); behavioral detection (Darktrace, speaker employer [S12]); cloud security building blocks (AWS community post [S10]); AI governance suite (IBM explainer [S8]); red-team and evaluation tooling; SIEM and SOAR; ITSM and case management; identity provider; data catalog and DLP; vector store and retrieval sources; regulator and auditor portals (evidence out).
  • Identity rules: one identity per agent, not a shared service account [S12]; least privilege and just-in-time access [S12] [S7]; human approval for high-risk actions [S7]; policy-engine admins separated from model builders (proposal).
  • APIs called out as patterns only: model provider API (LLM10 unbounded consumption [S7]), gateway policy API, registry API, evidence export API. Quotas and gov-cloud endpoints UNVERIFIED.
  • Boundary flows: prompts and completions, retrieved content (untrusted), interaction records to SIEM, incidents to ITSM, model versions into the registry, evidence packs to auditors.
  • Full note: 04 - Integration and AI Elements.
  • AI elements and AI data path
  • In scope: AI data path from training data and prompts, through model and guardrail layers, to outputs and monitoring. Covers LLM apps, RAG, agents and classical ML models.
  • Features: LLM application [S7]; retrieval-augmented generation [S7]; AI agent [S7] [S12]; classical ML model [S9] [S2]; third-party hosted model [S7].
  • Control points: CP1 label and map training data; CP2 evaluate before release; CP3 inspect input; CP4 access check and untrusted-content handling on retrieval; CP5 scoped tool call; CP6 inspect output; CP7 log the interaction; CP8 monitor drift and behavior.
  • Red points on that path: CP3 (prompt) and CP4 (retrieved content) [S7].
  • Oversharing stop is not one product. It is C7, realized by the data map, input and output inspection, and least privilege on tools. System-prompt restrictions alone can be bypassed [S7].
  • Hands-on lab
  • Access: Docs and desk only. No installs or tenant changes. Evidence tests are desk-based; any lab test stays unrun until an install or capture GO.
  • Desk work is the proposed build order in 05 - Detailed Design: evidence store, catalog, data map, policy, agent identity, gateway in monitor-only, evaluation gate, monitoring and incident hand-off, enforce mode per use case, first evidence pack against the NIST to ISO crosswalk [S4].
  • Do not run E3W (guardrail compare). It needs an install GO.
  • Failure modes and security
  • OWASP 2025 names [S7]: LLM01 prompt injection (full entry read [S7b]); LLM02 sensitive information disclosure (excerpt); LLM03 supply chain; LLM04 data and model poisoning; LLM05 improper output handling; LLM06 excessive agency; LLM07 system prompt leakage; LLM08 vector and embedding weaknesses; LLM09 misinformation; LLM10 unbounded consumption. Mitigation text beyond LLM01 and the LLM02 excerpt is UNVERIFIED.
  • LLM01 mitigations mix about two filtering items with about five privilege, architecture, or process items [S7b]. Treat the model as an untrusted user [S7].
  • Talks: an outer AI firewall if the model cannot be fixed, and red teaming first [S11]; filters cannot cover an infinite input and output space, so agent identity and over-permissioning matter [S12] (vendor interest).
  • Design failures: gateway as a single point of failure (fail-closed or fail-open is a proposal); vendor coverage claims before E3W; shared agent service accounts [S12]; evidence project bolted on after go-live instead of F8.
  • Debate 4 gap: safe, and fair with harmful bias managed, do not have a clearly named pillar [S2] [S9].
